# InventiX POS — the till

What it is, how it fits the system that already exists, and why each decision was made that way.
Written as it is built, one phase at a time.

Last updated 1 October 2026 — phase 1 (database and backend) complete.

---

## What it is

A sell screen for the shop counter. The cashier scans or searches a product, builds a bill, takes
cash, and the sale is recorded. Stock drops as the sale happens rather than at the end of the day.

**Who it is for:** shops that bill with a calculator and a notebook, and new shops. A shop that
already runs a POS keeps it — for those, InventiX reads the till's exported file instead. Replacing
a working cash register is a risk a shop owner has no reason to take.

## Where it sits

```
POS (shop's laptop)  ─┐
                      ├──→ backend ──→ database ──→ (realtime) ──→ owner's phone
InventiX app ─────────┘
```

The POS is **another client of the same backend**, not a separate system. There is no POS API: a
sale is an endpoint on the API the app already uses. The owner's Stocks screen updates by itself
because `stock_items` is in the realtime publication (migration 0019).

**Where the code lives:** `frontend/app/(pos)/`, a route group beside `(customer)` and
`(supplier)`, so it shares login, the API client, the theme and the catalog. It becomes its own app
only if it turns out to be a product of its own; moving a folder later is a day's work, while
un-copying code that has drifted apart is much worse.

**How it reaches a laptop:** the web build, installed from Chrome as a PWA, so it opens in its own
window and works with no internet. A packaged `.exe` (Tauri) is only needed if cash-drawer control
or sturdier storage demands it.

## Phase 1 — what was built

### Database

**`0025_pos_adjustment_reasons.sql`** adds `pos_sale` and `return` to the reasons a quantity may
change. The list is closed on purpose: every number in the app traces to a known cause. Reusing
`manual` would have made a cashier's sale indistinguishable from the owner correcting a miscount.

**`0026_pos_sales.sql`** adds:

| Table | Holds |
|---|---|
| `pos_sales` | One row per bill: receipt number, device, time, payment method, total, discount |
| `pos_sale_items` | One row per line: product, quantity, unit price, line total, how much came back |

and changes `sales_records`, which Reports read, so a sale no longer has to come from an uploaded
file: `upload_id` is now optional, and each row says whether its `source` is `upload` or `pos`.
A check constraint makes sure each row carries exactly the right link for its source.

Both new tables are **readable by their owner and writable only by the backend**, the rule
migration 0024 applied to orders, stock and ratings.

### Decisions worth defending

**The receipt number is generated by the till, not the server.** A till that is offline cannot ask
for the next number, so the number carries a device prefix: `T1-000147`. Unique per shop, enforced
by the database. Without a readable number, a customer returning something has nothing to quote.

**A sale is a record, not a request.** The customer has paid and left. The backend therefore never
refuses a bill over stock arithmetic:

- Sold 5 of something the system thinks it has 2 of → the bill keeps 5, stock stops at 0.
  Same clamp the sales upload already uses. The shop miscounted; the sale still happened.
- Sold a product that is not in Stocks → the sale is recorded, no stock moves.
- A stock id belonging to another shop → **refused**. That is not a counting error, it is a wrong
  write.

**The total is computed on the server.** The till sends lines; the backend sums them. A client that
can name its own total can under-report takings.

**Sending the same sale twice stores it once.** Each bill carries a `client_sale_id`, unique per
shop in the database. A till that times out and retries gets the first result back instead of
billing the customer twice — the same guarantee ordering already has.

**Stock moves through `apply_stock_adjustment`**, like every other quantity change, so the new
quantity and the row explaining it commit together. If that call fails, the failure is logged and
the bill is still kept: a shop can correct a count, but it cannot recover a sale it never recorded.

**Weighed goods round, not truncate.** Bills keep 1.255 kg; stock and sales history count whole
units and round. Truncating would quietly lose stock on every weighed sale.

**The day's summary counts cash separately.** A card payment never reached the drawer, so counting
it in would make every honest till look short.

**Times come from the till**, not the server: a bill made offline may arrive hours later. The day
boundary uses the shop's own date in Colombo, because on a UTC host `today` is yesterday until
5.30am.

### Backend

`backend/app/feeds/customer/pos/` — four endpoints:

| Method | Path | Purpose |
|---|---|---|
| POST | `/customer/pos/sales` | Record a finished bill. Safe to resend. |
| GET | `/customer/pos/sales` | The day's bills |
| GET | `/customer/pos/sales/{receipt_no}` | Find one bill, for a return |
| GET | `/customer/pos/summary` | Day close: bills, totals, cash expected |

The rules live in `backend/app/domain/pos.py` as plain functions — receipt format, line and bill
totals, how far stock may move, how much of a line is still returnable — so they are tested without
a database (`tests/test_pos.py`, 24 tests).

## Known limits

- While a till is offline the owner's phone shows stale stock. It catches up on reconnect.
- Returns are planned but not built: the tables and the rules are ready, the endpoint is not.
- VAT-registered shops (turnover over Rs. 60M a year) will eventually need an IRD-approved
  "secured POS" connected to the national e-invoicing system. A small shop is below that line.
